# DG 2.0 — Feature Brief (5 Oct 2026)

New capabilities to extend citizen self-service, officer scheme onboarding, and inclusive access (voice + location).

---

## 1. Check Eligibility (Guest)

**Goal:** Allow a guest (no login) to enter basic details and see which schemes they may be eligible for.

**Scope**
- Guest form: age/DOB, gender, caste category, district/taluka/village, annual income, education, marital/employment status (as available).
- Run eligibility against published scheme rules (same engine used for logged-in recommendations).
- Show matched schemes with short reason lines (why eligible / why not, if partial).
- CTA: Login / Apply for matched schemes; optional save session after OTP.

**Impact**
- Citizens discover benefits before registration.
- Government increases scheme awareness and uptake.
- Aligns with “government comes to citizen.”

---

## 2. Nearby Offices / Service Centers (Map + Filters)

**Goal:** For an eligible (or selected) scheme/service, show where the citizen can apply—based on current location (mobile/web) or manual geography filters.

**Scope**
- Inputs: device geolocation (with consent) **or** district / taluka / village selection.
- Output: list of Jan Seva Kendras / Mamlatdar / department offices linked to that service.
- Views: map pins + list (distance, hours, contact, “Get directions”).
- Scope by scheme/service where office type differs.

**Impact**
- Citizens know the nearest physical touchpoint.
- Reduces wrong-office visits; supports last-mile delivery.

---

## 3. Scheme Document → Eligibility Extraction (Officer Approve → DB)

**Goal:** Officer uploads scheme document (Word/PDF); system extracts eligibility criteria for review; on approval, criteria are persisted to the scheme DB.

**Scope**
- Upload: `.docx` / `.pdf` on Scheme Management (or formulation flow).
- Pipeline: OCR/text extract → AI/rules parse → structured criteria (fields, operators, values).
- Officer UI: editable extracted rules + source highlights; Approve / Reject / Edit.
- On Approve: write criteria to scheme engine DB (same model as manual rule builder).
- Audit: document version, extractor version, approver, timestamp.

**Impact**
- Faster scheme onboarding from policy PDFs.
- Consistent digital rules; less manual re-keying; human oversight retained.

---

## 4. Voice Bot Eligibility Assistant

**Goal:** Citizen speaks about themselves; voice bot responds with schemes they appear eligible for.

**Scope**
- Channels: citizen web widget and/or mobile app (mic + spoken reply).
- Flow: voice → STT → structured profile slots → eligibility engine → TTS reply + on-screen scheme cards.
- Languages: English + Gujarati (parity with existing bilingual UX).
- Guardrails: “indicative eligibility”; confirm via form/login before apply; privacy notice for voice data.

**Impact**
- Inclusive access for low-literacy / hands-busy users.
- Same proactive discovery, spoken instead of typed.

## Current tech stack — feasibility

All four features are **doable on the existing stack** without replacing the platform.

| # | Feature | Feasible? | Reuses |
|---|---------|-----------|--------|
| 1 | Guest Check Eligibility | Yes | `scheme-engine-service`, `RuleEvaluatorService`, citizen portal |
| 2 | Nearby offices (map + filters) | Yes | Web geolocation / Flutter; **new** office master (lat/lng, JSK/Mamlatdar) |
| 3 | Document → criteria → officer approve | Yes | `CustomRule` / `RuleCondition`, Scheme Management UI; **new** extract pipeline (PDF/DOCX + LLM) |
| 4 | Voice bot eligibility | Yes | `ai-intelligence-service` STT/TTS, `ChatWidget` voice; guest eligibility API (#1) |

**Not eligibility:** **Flowable** (certificate/pension/family/scheme-application workflows) and **DIGIT egov-workflow-v2** (e.g. marriage) handle **process**, not scheme eligibility rules.

---

## Rule engine in use today

Eligibility does **not** use Drools, Easy Rules, or Camunda.

| Component | Role |
|-----------|------|
| **`RuleEvaluatorService`** (`scheme-engine-service`) | Custom Java engine: `RuleCondition(field, operator, value)` + AND/OR logic |
| **Fields** | income, age, caste, gender, district, education, marital_status, employment |
| **Operators** | `<=`, `>=`, `=`, `!=`, `IN`, `NOT_IN` (education uses ordered levels) |
| **`CustomRule`** (JSON in Postgres) | Officer-defined rules; simulator and identification consume same model |
| **`SchemeEngineService`** | Scheme-level checks (caste lists, income ceiling, district scope, student schemes, etc.) + auto-identification |
| **AI (`ai-intelligence-service`)** | LightGBM ranker + Gemma — **ranking / explanation**, not authoritative eligibility |

Guest eligibility, voice eligibility, and document-approved rules should **extend this model**, not introduce a second rule language unless we deliberately migrate.

## Should we adopt a dedicated rule engine (Drools, etc.)?

**Short answer:** **Not required for the next phase.** **Plan for it** if rule volume, versioning, and non-developer authoring become pain points.

| Stay with custom engine (now) | Consider Drools / similar (later) |
|-------------------------------|-----------------------------------|
| Rules already map to `RuleCondition` + scheme fields | Hundreds of schemes × many conditions per scheme |
| Small, auditable, easy to explain in demos | Business users must edit rules without releases |
| Fits guest API, doc-extract → approve → same JSON | Complex rule chaining, decision tables, effective dates |
| Team owns the code path end-to-end | Need standard RETE/decision-table tooling and compliance narrative |

**Recommended approach**

1. **Now:** Extend `RuleEvaluatorService` + schema (new fields/operators as needed); keep **one** rule representation (`RuleCondition` / scheme criteria) for guest, logged-in, identification, and officer-approved doc extract.
2. **Near term:** Add **rule versioning**, effective dates, and tests per scheme (JUnit + fixture families) before rule count explodes.
3. **Trigger for Drools (or DMN):** e.g. **>50 active schemes** with **>10 conditions each**, or mandatory **business-owned** rule maintenance — then migrate evaluator behind an interface so portals/APIs stay unchanged.

**Do not** run Flowable or workflow engines for eligibility; keep eligibility in **scheme-engine-service** and workflows in Flowable/DIGIT as today.
